# Введение: реактивный подход и модель Combine

Эта глава адресована читателю, который ранее не работал с реактивными
библиотеками и не знаком с фреймворками Apple. Она объясняет, зачем
нужна модель «издатель — подписчик», чем она отличается от привычных
средств языка Swift и стандартной библиотеки, и как устроено
взаимодействие между сторонами потока данных. Все примеры на этой
странице компилируются и выполняются в тестовом наборе
`Tests/DocumentationExamplesTests`, поэтому приведённые результаты
соответствуют реальному поведению библиотеки.

## Проблема, которую решает реактивный подход

<!-- example: intro/why-reactive -->

Обычный способ передать куда-либо уведомление о событии — вызвать
замыкание (колбэк). Такой код короток, однако плохо масштабируется,
когда событий становится много, требуется фильтрация, преобразование и
объединение нескольких потоков:

```swift
// Императивный стиль: каждое событие — отдельный вызов замыкания.
final class Counter {
    var onChange: ((Int) -> Void)?
    private(set) var value = 0

    func increment() {
        value += 1
        onChange?(value)
    }
}

let counter = Counter()
counter.onChange = { value in
    print("value is now \(value)")   // обработчик пишется вручную
}
counter.increment()
// Обработчик вызван один раз со значением 1.
```

Реактивный подход предлагает иное описание: событие представляется
не вызовом, а *последовательностью значений во времени*, к которой
можно подключиться, объединять с другими последовательностями и
описывать преобразования декларативно, до того как первое значение
вообще появится.

## Издатель, подписчик, подписка

<!-- example: intro/publisher-subscriber -->

Три сущности образуют каркас библиотеки. *Издатель* (`publisher`)
производит последовательность значений. *Подписчик* (`subscriber`)
получает их. Между ними находится *подписка* (`subscription`) —
управляющий канал, по которому подписчик запрашивает значения, а
затем отменяет приём. Ниже показан минимальный пример подключения
готовым подписчиком `sink`, возвращающим маркер отмены:

```swift
let subject = PassthroughSubject<Int, Never>()

var received: [Int] = []
let token = subject.sink { received.append($0) }

subject.send(1)
subject.send(2)
// received == [1, 2]

token.cancel()
subject.send(3)
// received == [1, 2] — после отмены значения не поступают
```

Слово `PassthroughSubject` означает издатель, который не хранит
значений и лишь передаёт подписчикам всё, что в него отправляют;
он подробно разобран в [SUBJECTS-AND-STATE.md](SUBJECTS-AND-STATE.md).

## Отмена и жизненный цикл подписки

<!-- example: intro/subscription-cancel -->

Маркер `AnyCancellable`, возвращаемый подпиской, отменяет приём
значений; если маркер уничтожается без явного вызова `cancel()`,
отмена выполняется автоматически. Это защита от «подвешенных»
подписок, о которых никто не помнит:

```swift
var bag = Set<AnyCancellable>()
let subject = PassthroughSubject<String, Never>()

var received: [String] = []
subject.sink { received.append($0) }.store(in: &bag)

subject.send("a")
bag.removeAll()          // отмена всех сохранённых подписок
subject.send("b")
// received == ["a"]
```

Обратите внимание: отменённая подписка не порождает ни значений, ни
повторных завершений; её состояние окончательно.

## Спрос: почему издатель не «пушит» значения

<!-- example: intro/demand-basics -->

Центральное отличие модели Combine от простой рассылки колбэков —
управляемая доставка. Подписчик заранее объёмом *спроса* (`demand`)
— числом `.max(n)` или `.unlimited` — указывает, сколько значений
готов принять. Издатель не имеет права передать больше, чем
запрошено; избыточные значения в этой модели не копятся в буфере, а
отбрасываются, пока спрос не появится. Поведение видно на субъекте
с подписчиком, который запрашивает значения вручную:

```swift
let subject = PassthroughSubject<Int, Never>()

let subscriber = ManualDemandSubscriber<Int, Never>()
subject.subscribe(subscriber)

subject.send(1)              // спроса нет — значение отброшено
subscriber.request(.max(2))  // теперь спрос равен двум значениям
subject.send(2)
subject.send(3)
subject.send(4)              // спрос исчерпан — значение отброшено
// subscriber.values == [2, 3]
```

Такой механизм называют *бэкпрешером* (backpressure): потребитель
управляет скоростью producers, а не наоборот. Подробности арифметики
спроса приведены в [CONCEPTS.md](CONCEPTS.md).

## Завершение потока и отсутствие данных

<!-- example: intro/completion-vs-empty -->

Поток завершается ровно один раз, и завершение передаётся отдельно
от значений: либо штатно (`.finished`), либо с ошибкой
(`.failure`). Пустой поток — это не «ничего не произойдёт», а
поток, который немедленно завершается:

```swift
var events: [String] = []

let empty = Empty<Int, Never>().sink(
    receiveCompletion: { _ in events.append("finished") },
    receiveValue: { _ in events.append("value") }
)
empty.cancel()
// events == ["finished"] — завершение пришло, значений не было
```

Разделение «значение» и «завершение» позволяет подписчику отличать
конец данных от их отсутствия, что принципиально отличает модель от
итераторов, где конец последовательности обозначается одним и тем же
`nil`.

## Ошибки как часть типа потока

<!-- example: intro/error-stream -->

Тип потока фиксирует не только тип значений, но и тип ошибки.
Благодаря этому обработка ошибок не требует ни исключений, ни
проверки возвращаемых кодов: неудачное завершение — обычное
значение в канале завершений:

```swift
struct ParsingError: Error { case malformed }

var results: [String] = []

let failing = Fail<Int, ParsingError>(error: .malformed)
    .catch { _ in Just(-1) }          // заменить поток резервным
    .sink { results.append("\($0)") }
// results == ["-1"] — ошибка перехвачена и заменена значением
```

Оператор `catch` подключает резервный издатель в случае ошибки; семейство
операторов разобрано в [OPERATORS.md](OPERATORS.md#error-handling).

## Сравнение с итератором

<!-- example: intro/compare-iterator -->

Итератор выдаёт значения *синхронно* по запросу: пока код не вызовет
`next()`, ничего не происходит. Издатель же активен сам по себе и
готов отдавать значения *асинхронно*, когда бы они ни возникли; со
временем эту разницу сглаживает свойство `values`, превращающее
издателя в асинхронную последовательность:

```swift
var iterator = [1, 2, 3].publisher.values.makeAsyncIterator()
// Асинхронное получение: каждое next() запрашивает одно значение.
var collected: [Int] = []
while let value = await iterator.next() {
    collected.append(value)
}
// collected == [1, 2, 3]
```

Для потоков, которые завершаются неизбежно, итератор остаётся
удобным интерфейсом; для потоков, управляемых извне (пользовательский
ввод, сетевые события), предпочтителен издатель.

## Сочетание с обычным кодом

<!-- example: intro/combine-with-plain -->

Издатели не заменяют обычные значения и коллекции — они с ними
соседствуют: коллекция превращается в издатель одной строкой, а
итог конвейера снова является обычным значением:

```swift
let numbers = [1, 2, 3, 4].publisher   // коллекция -> издатель

var squares: [Int] = []
let token = numbers
    .map { $0 * $0 }                   // декларативное преобразование
    .sink { squares.append($0) }       // возврат к обычному коду
token.cancel()
// squares == [1, 4, 9, 16]
```
